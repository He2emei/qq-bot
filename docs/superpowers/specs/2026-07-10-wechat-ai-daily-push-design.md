# 微信 AI 早报自动推送恢复设计

## 背景与目标

现有机器人每分钟读取 `https://imjuya.github.io/juya-ai-daily/rss.xml`，把最新一期规范化为 `RssEntry`，再完成新闻分类、重点关键词筛选、QQ 普通消息和合并转发。旧站及 RSS 已停在 2026-06-08，作者目前通过微信公众号“橘鸦Juya”和同名哔哩哔哩账号发布早报。

本次恢复保留现有 QQ 展示、关键词和群组配置，替换失效的内容发现与获取链路。最终系统应同时支持：

1. 通过哔哩哔哩最新投稿发现当天微信文章，并关联视频链接。
2. 按参考 `client.py` 接入私有微信接口，通过公众号最新文章列表直接发现微信文章。
3. 任一发现源故障时自动使用下一来源；正文获取或解析不完整时不得推送或更新去重状态。
4. 同一期内容不会重复发送；部分群发送失败时只重试失败群。
5. API 密钥、签名密钥和运行状态不进入版本库。

## 已验证事实

- 2026-07-10 微信文章无需登录即可通过移动微信 User-Agent 获取，页面包含标题、公众号名称和完整的 `#js_content` 正文。
- 现有 HTML 分类器可从该正文识别 27 条新闻及全部栏目；微信页面把正文来源链接呈现为纯文本，因此需要补充 URL 提取逻辑。
- 哔哩哔哩账号固定 MID 为 `285286947`，名称为“橘鸦Juya”。最近 19 期符合 `【AI 早报 YYYY-MM-DD】` 的投稿中，18 期简介带有对应 `mp.weixin.qq.com/s/...` 链接。
- 哔哩哔哩搜索接口在缺少匿名浏览会话时可能返回 412；先访问站点主页取得公开会话 Cookie 后可正常访问，无需登录 Cookie。
- 参考 `client.py` 的 `/api/extract` 当前可以提取指定微信文章；`/api/search`、`/api/latest_articles` 当前分别出现服务端错误、公众号未收录或会话失效。因此私有接口不能阻塞第一阶段上线，且必须放在可回退的独立适配器内。

## 方案比较与决定

### 方案一：仅使用哔哩哔哩发现

实现最快，并且视频简介天然提供微信正文链接和视频 BV 号。但近期样本存在 1/19 缺链，不能作为最终唯一来源。

### 方案二：仅使用私有微信接口

概念上最直接，但当前最新文章接口无法对目标公众号完成一次有效调用。把上线依赖于该外部服务会继续导致功能不可用。

### 方案三：可插拔的双发现源

先用哔哩哔哩恢复生产链路，随后加入私有微信接口。最终顺序为微信接口优先、哔哩哔哩回退；正文始终以微信文章为准。这是选定方案。

## 分阶段交付

### 第一阶段：哔哩哔哩发现 + 微信正文

- 建立匿名哔哩哔哩会话并搜索最新投稿。
- 只接受 MID、标题日期格式和作者都匹配的早报投稿。
- 从视频简介提取微信文章链接；简介缺链时再查询该 BV 的详情一次。
- 直接获取微信 HTML，验证公众号和文章日期，规范化后复用现有分类与 QQ 推送。
- 保存视频 URL，使合并转发继续包含“哔哩哔哩视频版”。

### 第二阶段：私有微信发现 + 哔哩哔哩回退

- 移植 `client.py` 的签名规则和 `/api/latest_articles`、`/api/extract` 能力。
- 私有微信接口成为首选发现源；缺少配置、请求失败、响应无效或目标公众号未收录时，自动退回第一阶段的哔哩哔哩来源。
- 微信页面直接获取失败时，可以使用 `/api/extract` 的 Markdown 结果作为正文提取回退。
- 哔哩哔哩发现仍负责补全视频链接；即使微信接口先发现文章，也会在同日投稿中匹配对应 BV。

## 架构与组件

### `DailyIssueCandidate`

发现层只返回候选元数据，不负责正文解析或推送：

- `title`
- `article_url`
- `published_at`
- `issue_date`
- `source_id`（微信链接或 BV 号）
- `video_url`（允许暂时为空）
- `discovered_by`（`wechat_private` 或 `bilibili`）

### 发现源接口

统一接口 `discover_latest() -> DailyIssueCandidate`，两个实现彼此独立：

- `BilibiliDailySource`
- `WechatPrivateDailySource`

`DailyIssueDiscovery` 按配置顺序调用来源。来源抛出的网络、认证、风控、响应格式和无匹配结果错误会被记录，然后继续下一来源；所有来源都失败时抛出汇总错误。

发现完成后，协调器会调用哔哩哔哩适配器的 `find_by_date(issue_date)` 补全视频 URL。该步骤只允许返回同一日期、同一 MID 的投稿，不会替换已经发现的微信文章；视频补全失败不会阻止正文推送，只会省略“视频版”链接。

### 哔哩哔哩适配器

适配器维护一个进程内 `requests.Session`：

1. 首次使用时访问哔哩哔哩主页，取得匿名 Cookie。
2. 调用按发布时间排序的视频搜索接口。
3. 过滤 `mid == 285286947`，并要求标题包含 `【AI 早报 YYYY-MM-DD】`。
4. 从简介提取 `https://mp.weixin.qq.com/s/<id>`。
5. 搜索简介缺链时查询视频详情；仍缺链则忽略该候选并报告“最新一期缺少微信链接”，不得回退并误推旧一期。
6. 遇到 412 时仅重建一次匿名会话并重试，之后交由调度器下一轮处理，避免紧密重试触发更多风控。

适配器只使用匿名公开会话，不读取或持久化用户的 B 站登录 Cookie。

### 私有微信适配器

签名完全遵循参考实现：

`md5(api_key + endpoint + timestamp + [body_md5] + api_secret)`

配置来自环境变量：

- `WECHAT_API_BASE_URL`
- `WECHAT_API_KEY`
- `WECHAT_API_SECRET`
- `WECHAT_ACCOUNT_NICKNAME`

未设置密钥时该来源标记为不可用并立即进入下一个来源。任何日志都不得包含密钥、签名或完整请求头。目标接口为：

- `GET /api/latest_articles`
- `GET /api/extract`

`/api/search`、多公众号合并和关键词搜索不属于本次运行链路。

### 微信正文获取与规范化

`WechatArticleService` 接受候选微信 URL：

1. 只允许 HTTPS 且主机严格等于 `mp.weixin.qq.com`。
2. 使用移动微信 User-Agent 请求，限制连接和读取超时，并保留最终跳转 URL。
3. 必须找到文章标题、公众号“橘鸦Juya”和 `#js_content`。
4. 从文章标题提取 `YYYY-MM-DD`；日期和候选日期不一致时拒绝。
5. 规范化为现有 `RssEntry`。`entry_id` 使用规范化微信文章 URL；`title` 使用日期字符串，保证现有日期展示继续工作。
6. `RssEntry` 在末尾新增有默认值的 `video_url` 和 `discovery_source` 字段，保持现有调用兼容。

若直接 HTML 获取失败且私有提取接口已配置，第二阶段允许调用 `/api/extract`，把 Markdown 标题、栏目、新闻段落和纯文本 URL 规范化到相同 `RssEntry` 结构。

### 新闻 URL 解析

现有 RSS HTML 优先从标题锚点获取来源链接。微信正文没有锚点，因此按以下顺序解析每条新闻 URL：

1. 标题中的有效 `a[href]`。
2. 该新闻正文范围内出现的第一个 HTTP/HTTPS 纯文本 URL。
3. 没有 URL 时保留空值，不因单条缺链拒绝整期文章。

URL 需要去除末尾中文、英文标点；图片地址和微信内部跳转地址不作为新闻来源。

### 推送编排与状态

保留 `#rssdaily`、`#rsskw` 命令和现有配置名称，避免破坏现有部署。内部日志和错误文案改用“AI 早报”而不是“RSS”。

自动流程为：

1. 发现最新候选。
2. 若所有目标群已发送该 `entry_id`，直接结束。
3. 获取并验证微信正文。
4. 分类新闻并构建普通消息与合并转发；若没有解析到新闻条目则拒绝推送。
5. 对每个尚未完成的群依次发送普通消息和合并转发。
6. 两次发送都返回成功后，才为该群记录完成。

状态文件保存当前一期的 `entry_id`、标题、文章链接、视频链接，以及每个群的完成时间。检测到新一期时创建新记录。若旧版状态的 `last_entry_id` 等于当前候选，则把当前配置的自动推送目标群视为已完成并直接迁移，避免升级后重复推送；遇到下一期时自然创建新记录。状态写入使用同目录临时文件加原子替换，避免进程中断产生半个 JSON 文件。

机器人离线跨过多期时只推送发现到的最新一期，与原 RSS 行为一致，不补发中间日期。

`#rssdaily` 使用同一发现、正文获取、校验、分类和格式化链路，但对命令所在群执行强制发送。手动发送成功后只记录该群完成，不改变其他自动目标群的状态；再次手动执行仍可强制重发。

### QQ 发送结果

当前 HTTP 回退路径中，普通群消息即使成功也返回 `None`，无法可靠记录群完成状态。本次会让普通消息与合并转发在 WebSocket 或 HTTP 成功时都返回非空结果，失败时返回 `None`。推送层据此决定是否写入群状态；不改变其他调用方的参数和使用方式。

## 配置与调度

新增配置：

- `AI_DAILY_SOURCE_ORDER`，第一阶段为 `bilibili`，第二阶段默认 `wechat_private,bilibili`。
- `BILIBILI_UPLOADER_MID=285286947`
- `BILIBILI_UPLOADER_NAME=橘鸦Juya`
- `BILIBILI_SEARCH_KEYWORD=橘鸦Juya`
- 微信私有接口四项环境变量。

默认轮询间隔从 60 秒改为 300 秒。调度器保持单实例和合并执行；一次失败只记录错误，下一周期重试。

## 错误处理

- 发现源失败：尝试下一来源；全部失败时不推送、不写状态。
- B 站 412：刷新匿名会话后重试一次。
- 私有接口 401/403、时间戳、签名或会话错误：记录来源和状态码，不记录响应中的敏感值，然后回退 B 站。
- 微信页面被验证页替换、公众号不符、日期不符或缺少正文：拒绝候选。
- 正文能获取但零新闻条目：拒绝推送，防止发送空早报。
- 单群发送部分失败：不标记该群完成；其他已成功群不重复发送。
- 状态文件损坏：保存损坏文件的错误日志并从空状态恢复，不覆盖正文或密钥配置。

## 测试设计

### 第一阶段单元测试

- B 站匿名会话建立、搜索结果过滤、标题日期提取和视频 URL 生成。
- 简介微信 URL 提取、详情回退、最新一期缺链时拒绝旧一期。
- 412 时只刷新并重试一次。
- 微信 URL 域名、公众号、日期和正文节点校验。
- 微信 HTML 的六类栏目、新闻编号、重点关键词和纯文本来源 URL 提取。
- `RssEntry` 新字段不破坏原 RSS 测试。
- 按群去重、部分失败重试和旧状态迁移。
- QQ HTTP 成功返回可判定结果。

### 第二阶段单元测试

- 无请求体和有请求体时的签名与 `client.py` 一致。
- 最新文章响应解析、配置缺失、认证失败、会话失效和 malformed JSON。
- 私有来源失败后调用 B 站来源。
- 私有来源成功时仍按日期匹配 B 站视频。
- HTML 获取失败时使用 Markdown 提取回退。

### 集成与实时验证

- 使用模拟 HTTP 响应完成“发现 → 微信正文 → 分类 → 格式化 → 两类 QQ 发送 → 状态”的端到端测试。
- 使用 2026-07-10 的 BV 和微信链接执行不发送 QQ 的实时冒烟测试，验证可发现 27 条新闻、六个栏目和视频关联。
- 标准测试不得依赖外网；实时测试使用显式命令运行，避免网络波动造成日常测试不稳定。
- 私有微信接口当前外部会话无效时，实时验证必须证明它失败后可回退 B 站；当服务端恢复目标公众号后，再验证其能作为首选来源发现同一期文章。

## 非目标

- 不抓取或下载 B 站视频。
- 不模拟微信客户端登录，不维护微信个人 Cookie，不绕过验证码。
- 不补发机器人离线期间错过的所有历史早报。
- 不重写现有新闻展示格式、关键词管理或 NapCat 连接架构。

## 完成标准

1. 第一阶段可从当天 B 站投稿发现微信链接，解析正文并通过现有 QQ 消息结构发送。
2. 第二阶段提供与 `client.py` 相同签名规则的微信来源，并在其不可用时自动回退 B 站。
3. 今日样本实时解析得到 27 条新闻、六个栏目、正确日期和视频链接。
4. 自动与手动触发共用同一发现、解析、校验和推送链路。
5. 重复轮询不重复发送；部分群失败仅重试失败群。
6. 所有新增和既有 RSS 单元测试通过，相关模块可成功编译。
7. 版本库中没有 API Key、API Secret、签名、登录 Cookie 或运行时状态。
